# OpenCode V2 and agent ownership: architectural evidence and limits

## 1. What materially changes versus V1, rather than merely being renamed?

### Takeaway
Verified against live official documentation on **2026-10-15**. The strongest interpretation is **a consolidation of OpenCode into a reusable, explicitly owned agent runtime**, not the invention of client/server agents or proof of a smarter model. V2 makes a shared service the default, makes admitted work and delivery boundaries explicit, separates network clients from genuinely in-process embedding, and replaces ad hoc plugin mutation with scoped domain extension APIs. These are documented architectural contracts, not independently tested implementation/performance findings. [V2 CLI](https://opencode.ai/v2/docs/cli/) · [V2 SDK](https://opencode.ai/v2/docs/build/sdk/) · [Plugin migration](https://opencode.ai/v2/docs/build/plugins/migrate-v1/)

### Cited Findings
- **Historical guardrail:** V1 already starts a TUI plus server, calls the TUI a client, publishes OpenAPI, supports multiple clients, exposes provider and agent endpoints, supports asynchronous prompts, child sessions, and session summarization. Do not describe any of those broad capabilities as V2 inventions. V1's normal TUI assigns a random server port; a separate `opencode serve` starts another server even when the TUI is running. [V1 server, explicitly historical comparison](https://opencode.ai/docs/server/)
- **The default ownership boundary changes:** V2 discovers or starts **one shared background server per user account**; every local client connects to it. That server owns sessions, configuration, integrations, permissions, and tool execution. A private server remains available via `--standalone`, or a specific server via `--server`. This is a stronger factual claim than simply “it has a server.” [V2 CLI](https://opencode.ai/v2/docs/cli/#background-service)
- **Network integration versus embedding becomes an actual distinction:** V1's `@opencode-ai/sdk` is described as a type-safe server client; `createOpencode()` starts a server and a client, with hostname/port options. V2's `@opencode/client` is the generated network client; **`@opencode/sdk` hosts the server in-process**, routes calls through its HTTP router in memory, opens no listener, and introduces no network hop. V2's host is explicitly closed/disposed, including Location services, fibers, router, and scoped plugin registrations. This is substantive, not just a package rename. [V1 SDK](https://opencode.ai/docs/sdk/) · [V2 client](https://opencode.ai/v2/docs/build/client/) · [V2 embedded SDK](https://opencode.ai/v2/docs/build/sdk/)
- **The product and build-your-own experience share a contract:** V2's build guide says its network client is the same client used by the TUI and desktop app. The generated client's methods/types come from the API contract; browser-compatible entrypoints omit process management, while Node service helpers discover, ensure, stop, and authenticate with a local service. [Build overview](https://opencode.ai/v2/docs/build/) · [Client](https://opencode.ai/v2/docs/build/client/)
- **Durable work admission is explicit:** `session.prompt` is documented as “Durably admit one session input and schedule agent-loop execution unless resume is false”; it returns an inbox item, not the eventual model answer. The inbox lists undelivered durable user/synthetic/compaction/move work by enqueue sequence. Pending inputs can be canceled or switched between `steer` and `queue`; steering wakes execution. This supports a real distinction between accepting work and completing it. [V2 API](https://opencode.ai/v2/docs/api/) · [Linked OpenAPI contract: session.prompt, session.inbox.list/update/cancel](https://opencode.ai/v2/openapi.json)
- **Scheduling is exposed in the actual interface:** Enter while working steers the active session; Ctrl+X then Enter queues a prompt. Compaction defaults to the next safe/step boundary; move also has a requested delivery boundary. Interrupt is defined as interrupting execution **owned by this OpenCode process**; resuming handles pending steering and next-in-line controls while queued prompts remain parked. This is coordination/scheduling semantics, not an evidenced cron/calendar scheduler. [TUI](https://opencode.ai/v2/docs/cli/tui/) · [Compaction](https://opencode.ai/v2/docs/compaction/) · [OpenAPI: session.move and session.interrupt](https://opencode.ai/v2/openapi.json)
- **Plugin architecture is rewritten, not newly introduced:** V1 plugins return an object of hooks/tools. V2 uses a stable plugin ID and `setup(ctx)`, domain-specific synchronous replayable transforms, live-operation hooks, scoped disposal, and durable plugin-scoped JSON storage. Transforms rebuild fresh state in registration order; a model request captures a stable executable tool snapshot, so later registry changes affect future snapshots. The important conceptual shift is from modifying a bag of internals toward explicit domain/lifecycle contracts. [Plugin migration](https://opencode.ai/v2/docs/build/plugins/migrate-v1/) · [Plugin API: transforms, tools, storage](https://opencode.ai/v2/docs/build/plugins/)
- **Provider independence is not new, but protocol handling has concrete V2 shape:** V2 documents its own native runtime packages for OpenAI Chat/Responses, Anthropic, Google, Azure, Bedrock, OpenRouter, xAI, etc.; migrated AI SDK packages retain an `aisdk:` prefix. Semantic model options, raw HTTP body overlays, and HTTP/WebSocket hooks are distinct layers. OpenRouter's native runtime is specifically recommended to preserve its request/reasoning behavior. Do not claim V1 lacked provider-specific behavior; this evidence establishes V2's explicit extension/dispatch model, not a complete V1 implementation diff. [Providers](https://opencode.ai/v2/docs/providers/) · [Migration: providers](https://opencode.ai/v2/docs/migrate-v1/#providers) · [Plugin request hooks](https://opencode.ai/v2/docs/build/plugins/#model-requests)
- **Compatibility is intentional but incomplete:** The live migration page lists **three** intentional breaking changes: plugins, server API/clients, and terminal config moving from layered `tui.json(c)` to global `cli.json`. Supported existing server config and `.opencode` definitions are intended to remain compatible; conversion is optional. (The locally loaded overview skill says two breaking changes; defer to the fetched live migration page.) [Migration](https://opencode.ai/v2/docs/migrate-v1/)

### Inferences
- The best before/after formulation is **“from client/server coding application toward a separately usable agent execution substrate”**, not “from monolith to client/server.” Evidence supports an architectural emphasis and stronger defaults; it does not establish that every ingredient is unprecedented. [V1 server](https://opencode.ai/docs/server/) · [V2 CLI](https://opencode.ai/v2/docs/cli/) · [V2 SDK](https://opencode.ai/v2/docs/build/sdk/)

### Gaps
- No independent testing, source-code audit, benchmark, production reliability evidence, or proof that this architecture is unique among agent frameworks was collected. Architectural contracts cannot justify claims that V2 codes better, is faster overall, or is categorically more reliable.
- There is no sessions guide in the published V2 index; `/v2/docs/sessions` returned 404. Session evidence therefore comes from the official API/OpenAPI, plugin session API, CLI/TUI, and compaction docs. [Official V2 index](https://opencode.ai/v2/llms.txt) · [API](https://opencode.ai/v2/docs/api/)

## 2. How durable and autonomous is it really, and what does continuity mean?

### Takeaway
Distinguish **durable admitted input**, **durable stored history**, **a process-independent UI**, and **arbitrary crash-safe side effects**. The first three have direct documentation; universal exactly-once execution does not. Compaction explicitly preserves a working representation of a task while admitting that representation is lossy. [CLI](https://opencode.ai/v2/docs/cli/) · [OpenAPI](https://opencode.ai/v2/openapi.json) · [Compaction](https://opencode.ai/v2/docs/compaction/)

### Cited Findings
- **A concrete non-desktop runtime exists:** `@opencode/sdk/workerd` runs inside Cloudflare Durable Objects using the object's SQLite storage, persisting durable events for eviction recovery, and replacing unavailable local filesystem/process services. Docs say correctness does not depend on `close()` running because eviction can skip cleanup. This is documented deployability and recovery design, not just a future aspiration; it is not evidence that unmodified local shell tools run in Workers or that every external effect is exactly-once. [Cloudflare SDK](https://opencode.ai/v2/docs/build/sdk/cloudflare/)
- **Admission is not exactly-once side effects:** Prompt hooks run before durable admission. Retrying an already pending/delivered ID returns its original admission; concurrent submissions can run hooks multiple times although only the first successful admission wins. Docs explicitly warn hooks are not an exactly-once side-effect boundary. Tool executors must cooperate with cancellation, including forwarding `context.signal` to cancellable work. [Plugins: prompt admission and tools](https://opencode.ai/v2/docs/build/plugins/)
- **Public event streaming is not a durable catch-up log:** Client event subscriptions are live-only, with **no replay or automatic reconnection**. A source failure ends current subscriptions; applications must subscribe again after recovery. Thus do not equate persisted internal events or inboxes with reliable replay to every client. [Client: stream events](https://opencode.ai/v2/docs/build/client/#stream-events)
- **Continuity is checkpoint-based and task-shaped:** V2 summarizes older context and retains approximately 15,000 recent tokens by default; later compactions update the same summary. The structured summary includes objective, requirements, decisions, completed/active work, blockers, next moves, and relevant files, so another agent could pick up the work. Original earlier messages remain stored even when not sent to the model. V1 had summarization already; V2's migration explicitly contrasts its checkpoint/token-budget approach with legacy tail-turn/pruning settings. [Compaction](https://opencode.ai/v2/docs/compaction/) · [Migration](https://opencode.ai/v2/docs/migrate-v1/#compaction) · [V1 server: summarize](https://opencode.ai/docs/server/#sessions)
- **Continuity has hard tradeoffs:** Compaction is lossy; large tool outputs/attachments may be shortened, and an overlong compaction input can omit the oldest exchanges. Fixed instructions/tool schemas cannot be compacted away. A context-length failure is compacted and retried once, not infinitely. Compaction uses the session's model, with no separate compaction model. [Compaction: limits](https://opencode.ai/v2/docs/compaction/#limits)
- **Native provider memory is useful but not freely portable:** Optional native compaction on supported OpenAI Responses deployments returns an opaque encrypted checkpoint. It works only with the same provider, model, and endpoint. Switching models continues from the original conversation instead. Overlong native compaction retries a smaller request rather than silently switching to an OpenCode summary. [Compaction: providers](https://opencode.ai/v2/docs/compaction/#providers)
- **Native transport semantics remain differentiated:** Supported OpenAI/xAI/Azure Responses routes can reuse a per-session WebSocket and unchanged request prefix, sending only added content where supported. xAI with default `store:false` sends full steps despite connection reuse. Failed sockets fall back to HTTP; plugins requiring HTTP observability stay on HTTP. These are concrete upload/observability tradeoffs, not benchmark proof of end-to-end speed. [Providers: WebSockets](https://opencode.ai/v2/docs/providers/#websockets)
- **Security is bounded authority, not a sandbox:** Ordered permission rules use last match, saved project approvals cannot override configured denies, and policies can hard-deny after permissions. But shell commands run with the host user's filesystem/process/network authority; directory inference is best effort. A custom child agent uses its own permissions, **not necessarily a subset of its parent's**. [Permissions](https://opencode.ai/v2/docs/permissions/) · [Agents](https://opencode.ai/v2/docs/agents/#modes)
- **Documented missing/inactive features matter:** Agent `request.headers/body` overlays are retained but **not yet sent by the session runner**; provider/model/variant request settings are the active alternative. LSP config is accepted/preserved, but V2 **does not run language servers, expose LSP tools, or produce diagnostics**; use project lint/typecheck/compiler commands. Persistent PTY routes are labeled prototype, and the HTTP/session surface is labeled experimental. [Agents: request](https://opencode.ai/v2/docs/agents/#request) · [Migration: supported fields](https://opencode.ai/v2/docs/migrate-v1/#supported-fields-without-direct-native-equivalents) · [API](https://opencode.ai/v2/docs/api/)

### Inferences
- “The session belongs to the runtime, not the window” is a defensible shorthand for the shared-service ownership model. Do not extend it to “your agent survives every crash/reboot and safely finishes everything.” [CLI](https://opencode.ai/v2/docs/cli/#background-service) · [Cloudflare SDK](https://opencode.ai/v2/docs/build/sdk/cloudflare/) · [Prompt admission caveat](https://opencode.ai/v2/docs/build/plugins/#prompt-admission)

### Gaps
- The reviewed docs do not establish general restart/reboot auto-resumption guarantees, transactionality of external side effects, cross-machine session migration without constraints, distributed exactly-once execution, or fault-tolerance SLAs. Avoid claiming them.
- Supported/native semantic boundaries can be described from docs, but completeness/parity across all providers and restoration after mid-tool failures would need implementation inspection and failure-injection testing.

## 3. What deeper philosophical interpretation is justified?

### Takeaway
The important argument is not “a new chatbot became more intelligent.” It is that useful agency increasingly depends on **who owns ongoing work, how intervention is scheduled, what is remembered, and which powers are authorized**. The following five points are interpretations grounded in the above contracts, not claims made by the maintainers or proof that V2 dominates competitors.

### Cited Findings
- The factual anchors are shared-service ownership; durable inbox admission and steering/queueing; separate network/embedded hosts; lossy and provider-native checkpoints; differentiated native protocols; and enforceable permission/policy evaluation. [CLI](https://opencode.ai/v2/docs/cli/) · [API contract](https://opencode.ai/v2/openapi.json) · [SDK](https://opencode.ai/v2/docs/build/sdk/) · [Compaction](https://opencode.ai/v2/docs/compaction/) · [Providers](https://opencode.ai/v2/docs/providers/) · [Permissions](https://opencode.ai/v2/docs/permissions/)

### Inferences
1. **The unit of product shifts from the conversation window to the entrusted job.** A service owns the session; a prompt is admitted as durable scheduled work; interfaces can connect to the same runtime. Philosophically, the “agent” is not merely the model that writes the next token but the system that maintains a commitment across interactions. Caveat: V1 already had sessions, APIs, and async prompting; V2 strengthens this framing rather than inventing persistence or agency. [V2 CLI](https://opencode.ai/v2/docs/cli/) · [V2 inbox contract](https://opencode.ai/v2/openapi.json) · [V1 server](https://opencode.ai/docs/server/)
2. **Agency starts looking like systems engineering rather than prompting.** Admission, ordering, cancellation, scoped lifecycle, and explicit ownership are classic runtime concerns. The architectural wager is that models become more useful when surrounded by accountable execution machinery, not only better prose instructions. Caveat: this is an architectural rationale, not measured reliability; non-replaying event streams and non-exactly-once hooks expose unfinished/limited reliability boundaries. [SDK](https://opencode.ai/v2/docs/build/sdk/) · [Plugins](https://opencode.ai/v2/docs/build/plugins/) · [Client event limits](https://opencode.ai/v2/docs/build/client/#stream-events)
3. **Human control evolves from turn-taking to supervision of ongoing activity.** Steering changes active work; queueing waits; interrupt and background controls separate stopping, redirecting, and observing. This supports a collaborator/supervisor relationship instead of a strict question-answer rhythm. Caveat: stronger autonomy increases the need for intelligible authority boundaries; shell permissions are not isolation and child permissions are not automatically attenuated. [TUI](https://opencode.ai/v2/docs/cli/tui/) · [API](https://opencode.ai/v2/openapi.json) · [Permissions](https://opencode.ai/v2/docs/permissions/)
4. **Identity/continuity resides partly in maintained task state, not in an unbroken context window.** Objective/decision/next-move checkpoints mean the task can remain recognizable while most earlier tokens leave active context. This resembles organizational handoff more than photographic memory. Caveat: summaries are lossy, and encrypted provider checkpoints expose a tension between richer native continuity and portability/inspectability. [Compaction](https://opencode.ai/v2/docs/compaction/)
5. **A neutral agent layer need not flatten all models into the same protocol.** Shared runtime/client/plugin contracts can coexist with native reasoning, transport, and compaction semantics. The interesting platform possibility is owning the workflow layer while swapping or composing model suppliers—without pretending providers are semantically interchangeable. Caveat: native encrypted state creates switching costs, and the docs do not establish market dominance or universal abstraction parity. [Providers](https://opencode.ai/v2/docs/providers/) · [Plugin request layers](https://opencode.ai/v2/docs/build/plugins/#model-requests) · [Native compaction limits](https://opencode.ai/v2/docs/compaction/#providers)

### Gaps
- No defensible conclusion about the **entire** October 2026 agent market follows from OpenCode docs alone. These notes support an architectural thesis for the coordinator to compare with separately researched landscape evidence, not claims that everyone else lacks durable workflows, native providers, or embedded runtimes.
- Most V2 pages supply no publication/update timestamp in fetched text. The date above is **verification/access date**, not a fabricated release date; V1 server and SDK pages visibly say “Last updated: Oct 15, 2026.” No precise V2 launch date was established from these sources. [V1 server](https://opencode.ai/docs/server/) · [V1 SDK](https://opencode.ai/docs/sdk/)
