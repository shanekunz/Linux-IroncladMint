# OpenCode V2: agent ownership, delegation, and the cost of trustworthy work

Research cutoff: October 15, 2026. This is a narrow conceptual/empirical contribution, not a complete V1/V2 feature comparison. Sources below were fetched as full pages, not inferred from search snippets. Proposed interpretations and experiments are explicitly separated from reported findings. No configurations were modified.

## 1. Why could a runtime matter beyond interface polish—and what would actually count as reliable delegation?

### Takeaway

The strongest case is not that another runtime makes models intrinsically smarter. It is that useful delegation requires a system that preserves an authorized objective, makes progress inspectable, survives interruption, accepts correction, and contains failure without making the human reconstruct the whole job. The skeptical question is whether it reduces that burden in practice, rather than merely relocating it from a terminal to a service and plugin ecosystem.

### Cited Findings

- **METR, July 10, 2025: a real-work randomized trial, not an agent benchmark.** Sixteen experienced contributors completed 246 actual issues in mature open-source repositories they knew well, with issues randomized to AI-allowed/disallowed. AI allowance increased completion time by 19%; developers nevertheless believed afterward that AI had sped them up by 20%. Tasks averaged approximately two hours; tools were primarily Cursor Pro with Claude 3.5/3.7 Sonnet. The relevant lesson is that perceived ease and actual accepted-work productivity can diverge—not that AI universally slows coding. METR explicitly disclaims generalization to most developers, other domains, or future tools. — [Original study and methodological explanation](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/).
- **Crucial update, February 24, 2026: do not present that 19% slowdown as the current frontier.** METR's follow-up covered 57 developers, 143 repositories, and 800+ tasks. Raw estimated changes in completion time were −18% for returning participants (confidence interval −38% to +9%) and −4% for new participants (−15% to +9%). METR calls these unreliable estimates of current productivity because of recruitment/task-selection effects, a pay reduction, and difficulty measuring time when people run concurrent agents. It believes acceleration likely improved, but calls its data very weak evidence for the magnitude. Its original page now labels the old results out of date. — [Follow-up, including the negative estimates and uncertainty](https://metr.org/blog/2026-02-24-uplift-update/); [historical-page warning](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/).
- **METR time-horizon documentation, last updated September 8, 2026:** a 50% horizon is the human-expert task duration at which a fitted curve predicts 50% agent success. It is not a measured interval of safe unattended operation. Tasks are primarily self-contained software/ML/cybersecurity work with clear algorithmic scoring. METR emphasizes that low-context human baselines, cleaner tasks, and algorithmic success differ from high-context professional work; holistic evaluation can materially lower performance. Measurements above 16 hours are unreliable with its current task suite, and the page is no longer actively updated. Do not infer an October model leaderboard from it. — [Definitions, methodology, limitations, and update history](https://metr.org/time-horizons/).
- **Anthropic production account, June 13, 2025:** durable resume, retry logic, checkpoints, tracing, and deployment coordination were needed because stateful agents' errors compound. The authors specifically say restarting from scratch is costly and that minor operational failures can derail an agent's trajectory. This is a first-party engineering account, not a randomized test proving any particular runtime improves correctness. — [Production reliability and engineering challenges](https://www.anthropic.com/engineering/multi-agent-research-system).
- **V1 was already extensible.** The V2 migration guide explicitly describes existing V1 providers, plugins, MCP configuration, agents, commands, and a V1 server API. V2 revises API contracts; it does not invent these categories. The fetched guide lists three intentional breaking changes: plugin API, server API/clients, and terminal configuration moving to global `cli.json`. V1 plugin implementations do not run in V2 merely by being moved or renamed. Native server-config conversion is optional. The page does not display a publication date; accessed October 15, 2026. — [Full V2 migration guide](https://opencode.ai/v2/docs/migrate-v1).

### Inferences

- **Philosophical framing: delegation is a revocable commitment, not just execution.** A human delegates an outcome under constraints, retaining authority to revise or cancel it. The system must connect intention, authority, action, evidence, and accountability across time. This is an analytical definition, not evidence that a runtime possesses agency, personhood, judgment, or moral responsibility.
- **The unit of progress should be an accepted change, not a generated diff.** A proposed accounting identity is: human burden = specification + supervision + correction + review + recovery + tool maintenance. Separately measure elapsed time, model/infrastructure money, and residual defect risk. A runtime matters substantively if it lowers this total at equal acceptance standards, even with the same underlying model. These criteria follow from the measurement problem in the METR studies and the operational failures in Anthropic's account; they are not established V2 outcomes. — [METR follow-up](https://metr.org/blog/2026-02-24-uplift-update/); [Anthropic engineering account](https://www.anthropic.com/engineering/multi-agent-research-system).
- **Do not turn recovery mechanisms into semantic guarantees.** Exactly preserving the wrong plan is not correctness; retrying a side-effectful action can duplicate damage. Resume must reconcile recorded intentions with actual filesystem/tool state and the user's latest correction. Operational continuity and task correctness are separate hypotheses to test. — Motivating observations: [stateful error handling](https://www.anthropic.com/engineering/multi-agent-research-system); [task-success limitations](https://metr.org/time-horizons/).
- **For this user, the bottleneck is already partly organizational.** Repository instructions describe Linux/i3, Stow, shared skills across Claude Code/Codex/OpenCode, reproducible installation scripts, and project-specific agent definitions. The assignment additionally supplies herdr usage, repo commands/MCPs, and an observed plugin migration requiring a new API and reload. Treat those latter details as coordinator-provided context, not independently reproduced evidence. The useful question is whether the tooling keeps these conventions coherent when models, sessions, and processes change—not whether it has another attractive interface. — [Repository context](../AGENTS.md); [documented API migration boundaries](https://opencode.ai/v2/docs/migrate-v1).
- **Ownership is more than where a service runs.** As an evaluative criterion, ownership means the user can inspect, revise, export, revoke, and replace the machinery and its task evidence without rebuilding everything. Shared repository skills already provide part of that portability; an OpenCode-specific plugin can simultaneously add value and create maintenance dependency. V1's existing APIs mean the V2 thesis has to be better composability/recovery/operation, not newly discovered openness. — [Repository context](../AGENTS.md); [migration guide](https://opencode.ai/v2/docs/migrate-v1).
- **Strong skeptical case:** the human may become an unpaid integration engineer for permissions, background services, MCPs, models, hooks, and versioned APIs. The migrated-plugin incident is a small but relevant example of this tax, not proof of systemic unreliability. Conversely, one migration failure does not establish that continued V1 maintenance or a different harness would be cheaper. UX improvements may still be valuable on their own if they measurably reduce cognitive load; “only UX” is not automatically a dismissal.

### Gaps

- No retrieved source establishes that OpenCode V2 reduces real-repository defect rates, review minutes, or recovery burden versus V1, Codex, or Claude Code. This requires direct testing.
- Neither a clean benchmark success nor a happy user report measures the full cost of supervising a long-lived, operationally fragile workflow. The historical slowdown and the current uncertainty should both be preserved, not selectively quoted.

## 2. Is persistent state the same as good memory or continuity of intent?

### Takeaway

There are at least four different continuities: surviving process/client interruption, restoring task execution state, recalling relevant evidence, and honoring the latest intent and permissions. A durable transcript or database can help the first two while failing the latter two. Better memory must include correction, provenance, supersession, and abstention—not simply more retained text.

### Cited Findings

- **LongMemEval, first submitted October 14, 2024; revised March 4, 2025; ICLR 2025:** 500 curated questions separately evaluate information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention. Its framework separates indexing, retrieval, and reading. This is a benchmark of compiled chat histories, with LLM-simulated/human-edited evidence sessions and sampled distractors, not a longitudinal study of developers. — [Full paper](https://arxiv.org/html/2410.10813v2).
- **Useful result with carefully bounded meaning:** the paper's GPT-4o result without Chain-of-Note falls from 0.870 accuracy with evidence-only context to 0.606 on approximately 115k-token histories—a 30.3% relative decrease, not 30 percentage points. Its small commercial-memory pilot used 97 questions, only 3–6 sessions, and was conducted in the first two weeks of August 2024. These numbers cannot responsibly describe October 2026 products. Their continuing relevance is methodological: distinguish memory creation/retrieval failures from failures to use the evidence, and test updated or unknown facts explicitly. — [Section 3.4 and Figure 3](https://arxiv.org/html/2410.10813v2#S3.SS4).
- **The same study finds that perfect retrieval is insufficient:** reading strategy and representation affect downstream answers even when the evidence is present. Compressing sessions into facts can lose detail, while different granularities help different question types. “Memory” is a pipeline with tradeoffs, not a single storage feature. — [Full paper, sections 4–5](https://arxiv.org/html/2410.10813v2).
- **Anthropic, June 13, 2025:** its research system externalizes plans, summarizes completed phases, retrieves stored context, and writes subagent artifacts to files rather than repeatedly passing everything through a coordinator. The stated rationale includes avoiding truncation, reducing the game-of-telephone loss, and lowering copied context. These are described engineering patterns, not proof they preserve every important constraint. — [Architecture and appendix](https://www.anthropic.com/engineering/multi-agent-research-system).

### Inferences

- **Storage is not belief revision.** To be useful after a correction, memory must distinguish “the user originally asked for X” from “the user now wants Y,” and “the agent proposed this” from “a test demonstrated this.” Versioned evidence and explicit supersession are better evaluation targets than transcript length. This inference is motivated by LongMemEval's separate knowledge-update, temporal, and abstention tasks. — [Memory taxonomy](https://arxiv.org/html/2410.10813v2).
- **A concrete resumption audit for this repository:** after an interruption, can the agent report the current objective; latest correction; changed files; commands actually run and their outcomes; remaining uncertainty; and which actions still need approval? Can it re-check Stow/idempotency and synchronized i3 keybind documentation without importing stale assumptions? These are proposed checks grounded in repository invariants, not observed V2 guarantees. — [Repository invariants](../AGENTS.md).
- **Persistence can preserve mistakes and stale authority.** A remembered permission should not become indefinite authority to execute a materially different action. Similarly, saving a failed install plan indefinitely is not institutional knowledge. This is a normative design requirement, not an empirical claim that a specific runtime violates it.
- **A task ledger can matter more than a simulated personality.** For this workflow, small durable artifacts—objective, constraints, evidence, pending approvals, test receipts, and rollback boundaries—may be more valuable than a universal personal-memory narrative. Repo-owned artifacts also give another harness something inspectable to pick up. This is a hypothesis consistent with Anthropic's external-artifact pattern and this repository's shared-skills approach, not a measured superiority claim. — [Artifact pattern](https://www.anthropic.com/engineering/multi-agent-research-system); [shared skills](../AGENTS.md).

### Gaps

- This research does not establish V2's actual memory-fidelity, compaction, or crash-recovery behavior. Do not infer those properties from its API redesign or from first-party descriptions of another product.
- LongMemEval's original results are old-model conversational evidence, not current coding-agent performance. Search discovery also indicated a newer agentic edition; it was not reviewed here, so no current leaderboard claim is made.

## 3. Does parallelism scale useful output, and how should this user falsify the runtime thesis?

### Takeaway

Parallelism is most credible when subtasks are genuinely separable and their outputs independently checkable. More agents can buy breadth and latency with more compute, but integration, shared-state conflicts, correlated errors, and review can dominate. The right personal trial measures accepted work and recovered intent under disruption—not agent count, tokens, or uninterrupted demo speed.

### Cited Findings

- **Anthropic, June 13, 2025:** an Opus 4 lead with Sonnet 4 workers outperformed single-agent Opus 4 by 90.2% on an internal research evaluation, especially breadth-first queries. It reports approximately 15× the tokens of chats for multi-agent systems and 4× for agents. **The 15× denominator is chat, not single-agent work.** The internal result uses a mixed-model system and is not a controlled equal-compute software-development comparison. The authors explicitly warn that most coding tasks are less parallelizable than research and that shared context/inter-agent dependencies limit suitability. — [Benefits and limitations](https://www.anthropic.com/engineering/multi-agent-research-system).
- **More current counterweight, Anthropic Frontier Red Team, August 13, 2026:** 45 agents in separate VMs coordinated vulnerability search across 15 open-source projects. A Mythos Preview swarm reported 266 findings over 27 million tokens versus 21 over 6.5 million tokens for independent agents, but search scopes differed. Restricting swarm findings to the core directories assigned to independent agents made tokens per vulnerability seem comparable. These counts do not establish a general efficiency multiplier; they mix more spending, wider search, and coordination. This is a first-party experimental account, not a real-world controlled productivity trial. — [Measuring coordination](https://www.anthropic.com/research/multiagent-systems).
- **Same August 2026 account:** 12-hour cooperative game-building simulations produced poor end products across tested prompts, even when newer models improved PR merging. The experiments also show correlated behavior, such as 18 of 30 agents initially choosing the identical branch name. The authors distinguish independent search from tightly coupled engineering and caution that individual intelligence does not automatically produce coordination. Do not generalize the game task into a universal failure rate. — [Coordination and conformity experiments](https://www.anthropic.com/research/multiagent-systems).
- **Measurement challenge already observed in the wild:** METR's February 2026 follow-up says developers often work on something else while an agent runs, making task time difficult to report. Therefore elapsed runtime, human active time, and total accepted throughput need separate accounting. — [Updated experiment design](https://metr.org/blog/2026-02-24-uplift-update/).

### Inferences

- **Useful distinction: parallel exploration versus parallel mutation.** Independent documentation research, read-only audits, and isolated test discovery are plausible wins. Multiple agents simultaneously changing the same installer orchestration, permission rules, or plugin API are tightly coupled work, even if each has its own terminal. File isolation alone does not eliminate interface/invariant dependencies. — Motivating contrast: [August 2026 experiments](https://www.anthropic.com/research/multiagent-systems).
- **Multiple agreeing reviewers are not necessarily independent evidence.** Same-model agents given the same assumptions can repeat an error. Require disconfirming tests, source receipts, or genuinely different evidence rather than treating consensus as verification. This is a proposed safeguard motivated by the documented conformity and epistemic failures, not a measured remedy. — [Conformity and epistemic failures](https://www.anthropic.com/research/multiagent-systems).

#### Proposed falsifiable trial: a small personal reliability study, not a leaderboard

The following is a proposed protocol, not an empirical finding:

1. **Preselect 8–12 real tasks before seeing which harness gets them.** Include an idempotent installer change; i3 binding plus synchronized help; Stow or script regression with a test; and a small plugin/API fixture. Use at least one genuinely separable read-only audit and one coupled multi-file implementation. Define acceptance checks before execution using the repository's invariants. Do not run installs or change live desktop settings during the experiment. — Task rationale: [repository rules](../AGENTS.md).
2. **Separate two comparisons.** For a runtime-effect comparison, use the same model/provider/settings, instructions, tools, permissions, initial commit, and budget in V1 and V2 where possible; record unavoidable differences. For a user-choice comparison, compare best-supported Codex/Claude Code/OpenCode workflows, explicitly acknowledging that model, defaults, and harness are then confounded. V1/V2 need isolated environments/config roots or disposable containers: the migration guide warns they share config locations and native V2 configurations should not be pointed at V1. — [Migration warning](https://opencode.ai/v2/docs/migrate-v1).
3. **Randomize order and avoid knowledge leakage.** Run fresh sessions against clean copies of the same starting state; do not feed one solution to the next arm. Repeat a few representative tasks because agent behavior varies. Record warmed caches, prior human familiarity, and tool-version differences. A small personal trial gives directional evidence, not population significance.
4. **Test four disruptions in disposable environments.** (a) Disconnect/close the client mid-task and reconnect; (b) stop and resume execution at a predetermined safe checkpoint, testing process recovery separately from mere client reconnection; (c) provide a correction after a plausible plan, then require it to survive resumption; (d) inject a temporary tool failure or incompatible mock plugin API requiring a reload. Do not restart a shared live service or break real credentials/plugins to manufacture a test.
5. **Test failure containment.** Place an unrelated sentinel file and an out-of-scope tempting fix in the sandbox. Verify they remain untouched. Test whether denied/unavailable tools cause an accurate limitation report instead of improvised broader authority. Check that interruption does not duplicate an already-completed side effect and that partial work is accurately reported.
6. **Audit the handoff.** After resumption, ask for objective, latest correction, changed files, actual test receipts, uncertainty, and remaining approvals; compare with ground truth. Record invented test success, resurrected rejected plans, repeated work, and unnoticed partial edits. Distinguish “transcript restored” from “task understood correctly.”
7. **Measure five axes separately.** Human active minutes including prompting/review/repair; wall-clock time to accepted patch; actual model/tool spending; maintenance and recovery minutes; and accepted quality/scope compliance. Include failed attempts, abandoned runs, plugin-porting time, and review of extra generated code. Review without harness labels where feasible. Re-check the patch the next day for missed defects.
8. **Ablate parallelism.** On suitable tasks compare one agent versus several at a matched token/money ceiling, and separately allow a larger multi-agent budget. Record integration/review minutes and final accepted output. Otherwise a result may demonstrate the value of more compute rather than coordination.
9. **Precommit a personal decision rule.** For example: prefer V2 if it reduces median active human time by at least 20% at unchanged acceptance/scope standards, recovers correctly from all selected interruption/correction cases, and repays migration/maintenance within a month of actual usage. These thresholds are illustrative preferences, not scientific constants. A severe containment failure is a veto regardless of speed; small samples cannot establish that severe failures are rare.

**What would falsify the optimistic story?** V2 produces faster first diffs but requires equal/more review and repair; loses the latest correction after recovery; silently disables a needed integration; repeats side effects; increases maintenance beyond its saved time; or more agents increase output without increasing accepted useful changes. In those outcomes, staying with V1 or using Codex/Claude Code is a rational result—not a failure to appreciate architecture.

**What would support it?** With comparable models and tasks, the user spends less time reconstructing context and supervising retries, obtains the same accepted quality, can recover or change direction with accurate evidence, and keeps failures local. That would make the runtime meaningfully more than surface UX without requiring an “AI OS” story or claiming V1 lacked APIs.

### Gaps

- No public result retrieved isolates the effect of OpenCode V2 architecture from model quality, tool design, budget, task selection, or human familiarity.
- Single-user trials will be noisy and cannot certify safety. Their advantage is relevance to this user's actual dotfiles conventions and operational interruptions, not broad statistical authority.
