# Model vendors, neutral harnesses, and ownership of agent execution

Research cutoff and retrieval: **October 15, 2026**. Sources below were fetched, not merely inferred from search snippets. Dates distinguish publication from retrieval; undated live documentation is evidence of the documented position at retrieval, not proof of when a feature launched. Scope: landscape and implications, not an exhaustive feature comparison or OpenCode implementation audit. All OpenCode facts come only from full relevant **V2** documentation pages. A guessed `/v2/docs/architecture` page returned 404 and supplies no evidence.

## 1. Who controls the agent: vendor integration, authentication, and economics?

### Takeaway
The meaningful contest is ownership of the execution environment and customer relationship, not simply whether a terminal offers multiple models. The current landscape is not a clean proprietary-versus-open binary: vendor products can expose open integrations or alternative providers, while independent harnesses remain subject to upstream authentication, eligibility, pricing, and capacity decisions. [Anthropic policy](https://code.claude.com/docs/en/legal-and-compliance); [OpenAI authentication](https://developers.openai.com/codex/auth); [Google transition](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli)

### Cited Findings
- **Anthropic: model API access and consumer subscription access are different rights.** Undated live legal/compliance documentation, retrieved Oct 15, says OAuth is for subscription purchasers' ordinary use of Claude Code/native Anthropic apps; developers building applications should use API keys or supported cloud providers. It explicitly prohibits third-party developers from offering Claude.ai login in their own applications, routing requests through Free/Pro/Max credentials on users' behalf, or collecting/storing/intermediating Claude.ai credentials. It reserves enforcement without prior notice. This is much stronger evidence than reports about an individual January OAuth cutoff. [First-party policy](https://code.claude.com/docs/en/legal-and-compliance)
- **Important exception: a third-party interface may host the actual vendor harness.** The same current Anthropic page permits platforms to preinstall/run the **unmodified Claude Code binary**, subject to commercial terms; they must preserve its authentication methods, each end user must authenticate under their own agreement, and the platform may not pay for/resell/intermediate usage on users' behalf. Native subscription sign-in to that unmodified binary remains allowed. Therefore “Anthropic bans all third-party environments” would be false. Distinguish an alternate frontend around Claude Code from replacing Claude Code's agent loop. [First-party policy](https://code.claude.com/docs/en/legal-and-compliance)
- **OpenAI currently documents a materially different route.** Undated live Sign in with ChatGPT documentation, retrieved Oct 15, explicitly lets eligible users spend their ChatGPT plan on eligible Responses API requests in **open-source and locally hosted apps**. Paid/remotely hosted apps are directed to an interest form; this is not unconditional universal portability. The app requests consent, registers a user-defined agent, and persists a host identifier; issued client registrations bind to a user/workspace. It does **not** give access to users' ChatGPT conversations or other account context. Requests are described with `store: false` and `stream: true`. [First-party overview](https://developers.openai.com/siwc/token-sharing-open-source.md); [landing page](https://developers.openai.com/siwc)
- **Do not equate a portable entitlement with portable memory.** The explicit exclusion of ChatGPT conversation/account context makes this a concrete case where model/billing access travels but the surrounding accumulated state does not. [First-party SIWC overview](https://developers.openai.com/siwc/token-sharing-open-source.md)
- **Codex itself is not purely closed to alternative models.** Current authentication docs describe custom providers with environment-key authentication or no authentication for local models; OpenAI-authenticated proxy providers can use `requires_openai_auth`. Thus “only independent harnesses can connect to local/custom models” is untenable. This establishes configuration support, not equal performance or all feature compatibility. [First-party Codex authentication](https://developers.openai.com/codex/auth)
- **Codex's identity path changes features and governance.** Current docs say ChatGPT desktop/Codex CLI/IDE extension support ChatGPT subscription login or API keys for local work, but Codex cloud requires ChatGPT sign-in. API keys use standard API billing, not included plan credits, and some workspace/cloud features and plugin OAuth connections are limited/unavailable. Subscription use follows ChatGPT workspace permissions/retention/residency; API-key use follows API-organization settings. [First-party authentication](https://developers.openai.com/codex/auth)
- **Google offers unusually clear 2026 evidence of consolidation around the harness.** May 19, 2026 announcement says Antigravity CLI shares the same agent harness as Antigravity 2.0 desktop, with a server-side harness, asynchronous multi-agent work, and unified future improvements. It says consumer Gemini CLI and Code Assist IDE access through free/Google AI Pro/Ultra would stop June 18, while enterprise licenses and paid API keys remain supported. Critical nuance: this is not “Gemini CLI ceased to exist,” nor proof all its open code became closed. [Google announcement, May 19, 2026](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli)
- **The open-client versus open-service distinction is visible in Google's own docs.** The Gemini CLI skills documentation was last updated Apr 30, 2026, but its current banner says unpaid/Google One users were transitioned June 18. Historical descriptions of its generous consumer free tier should not be presented as current October terms. [Current skills page/banner](https://geminicli.com/docs/cli/skills); [dated transition announcement](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli)
- **OpenCode V2 retains direct and local alternatives.** Its current providers page supports native OpenAI, Anthropic, Google, Vertex, Azure, Bedrock, OpenRouter and custom runtime packages/endpoints, plus local Ollama/LM Studio/vLLM discovery. The intro advertises optional OpenCode Go at $10/month; the provider page calls it optional. These establish technical alternatives and an optional commercial service, not a comparative cost advantage or proof every current frontier model is supported. [V2 providers](https://opencode.ai/v2/docs/providers); [V2 intro](https://opencode.ai/v2/docs/)
- **OpenCode is also a credential/state custodian.** Its V2 provider-account page says saved API keys/OAuth tokens live in the server SQLite database, supports multiple saved accounts and environment/native cloud credentials, and shows an OpenAI “Codex device code (legacy)” authentication example. That example does not establish that OpenCode has implemented every feature of OpenAI's newer SIWC flow. [V2 provider accounts](https://opencode.ai/v2/docs/cli/providers)

### Inferences
- **“Open source” is a governance/exit property, not immunity from upstream business power.** One can control client/runtime code yet lose subsidized inference access or have to pay API rates; Google's consumer transition and Anthropic's credential policy demonstrate the mechanisms. A defensible neutrality claim is preserving an exit route and bargaining flexibility, not independence from all providers. [Google](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli); [Anthropic](https://code.claude.com/docs/en/legal-and-compliance); [V2 alternative runtimes](https://opencode.ai/v2/docs/providers)
- **Subscription policy can affect competition as much as model quality.** An integrated product bundled with existing credits and identity may beat an alternative harness economically even if both invoke the same model API. Conversely, OpenAI's documented plan-sharing path can reduce that disadvantage for eligible independent apps. This is an economic mechanism, not a measured price ratio. [Codex auth/billing](https://developers.openai.com/codex/auth); [SIWC eligibility](https://developers.openai.com/siwc/token-sharing-open-source.md)
- **The landscape suggests competition over the developer's “place of work.”** Google's explicit unified-harness rationale and Anthropic's SDK reuse extend agent loops across tasks/interfaces. The strategic prize can be the permissions, context, integrations, and long-lived sessions through which intelligence acts, not merely API token revenue. This is interpretation grounded in product architecture, not a statement of confidential company intent. [Google](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli); [Anthropic SDK article, Sep 29, 2025](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)

### Gaps
- No controlled, representative October 2026 total-cost comparison across consumer plans, API rates, cache behavior, rate limits, and task success was established. Do not repeat anecdotes that API access costs “10x” a subscription.
- SIWC's overview is current but undated; launch date, full current eligibility, exact supported model list and availability for every third-party product were not verified. Do not retroactively attribute it to January 2026 or imply universal approval.
- Anthropic's current page establishes the present policy, not an independently verified history/timeline of specific enforcement incidents against OpenCode. Those incidents are unnecessary to the argument.

## 2. Are models commoditizing, and must neutral abstraction erase important differences?

### Takeaway
The evidence supports **multiple substitutable suppliers for some tasks**, not interchangeable intelligence. Both model differences and harness differences matter; neutrality is most credible as a stable workspace with provider-aware adapters, rather than a promise that every model behaves identically behind one API. [Meta-Harness research](https://arxiv.org/html/2603.28052v1); [V2 providers](https://opencode.ai/v2/docs/providers); [V2 models](https://opencode.ai/v2/docs/models)

### Cited Findings
- **A model name is not the full evaluated agent.** METR's current methodology says evaluations combine a model with a scaffold handling tools and interaction; researchers first elicit behavior on a dev set and choose among ReAct, Triframe, Claude Code, Codex, etc., adjusting spurious failures. This cautions against attributing all leaderboard differences to weights. The time-horizon page's last update is **Sep 8, 2026**, when METR clarified it is no longer actively updated; latest listed model additions are from May, not October. [Independent METR methodology/currentness notice](https://metr.org/time-horizons)
- **Independent research demonstrates a meaningful harness contribution, but not an October product ranking.** Lee et al., *Meta-Harness*, arXiv v1 dated **Mar 30, 2026**, reports TerminalBench-2 pass rates for the same Haiku 4.5 model: Claude Code 27.5%, Terminus-KIRA 33.7%, their searched harness 37.6%. For Opus 4.6, its table reports Claude Code 58.0%, Terminus-KIRA 74.7%, searched harness 76.4%. Other agents' values were copied from a leaderboard, not necessarily reproduced under identical conditions. Treat as research evidence of harness sensitivity, not a definitive fair product comparison. [Paper §4.3/Table 7](https://arxiv.org/html/2603.28052v1)
- **Major limitation of that evidence:** the paper explicitly performs coding-harness search and final evaluation on the **same 89 TerminalBench-2 tasks**, using code inspection/string audits rather than a held-out coding split. There is an internal ranking inconsistency: Table 7 lists ForgeCode above Meta-Harness and several lower agents, while text calls Meta-Harness #2 despite leaderboard comparability concerns. Avoid quoting leaderboard placement as a durable fact. The authors acknowledge inability to reproduce ForgeCode from public code. [Paper §4.3](https://arxiv.org/html/2603.28052v1)
- **There is some evidence that useful harness strategies transfer between models.** The same paper's separate **math**, not coding, experiment searches a retrieval harness using GPT-OSS-20B then evaluates it across five models, including four unseen in search. Average gain over no retrieval is 4.7 percentage points across 200 previously unseen IMO-level problems. Individual gains differ (+1.6 to +8.7), and the underlying no-retriever accuracies differ substantially. This supports transfer of some orchestration ideas without demonstrating general model interchangeability. [Paper §4.2/Table 6](https://arxiv.org/html/2603.28052v1)
- **Source independence qualification:** Meta-Harness is academic research from Stanford/MIT/KRAFTON authors, not an agent vendor comparison blog, but acknowledges OpenAI/KRAFTON support and uses Claude Code/Opus as proposer. It is an arXiv preprint, not established here as peer-reviewed. [Paper author list, implementation and acknowledgements](https://arxiv.org/html/2603.28052v1)
- **Neutrality need not mean lowest-common-denominator transport.** OpenCode V2 documents native provider runtime packages, custom package support, provider/model/variant-specific settings/headers/body, explicit capabilities/context limits, custom streamed reasoning fields, prompt-cache compatibility overrides, and provider-specific WebSocket behavior. It warns other packages may ignore/reject provider-specific options. This is concrete evidence of a neutrality design that preserves distinctions instead of pretending they do not exist. [V2 providers](https://opencode.ai/v2/docs/providers); [V2 models](https://opencode.ai/v2/docs/models)
- **Concrete abstraction costs are visible.** V2 docs say Anthropic-style cache breakpoints through OpenAI-compatible proxies such as LiteLLM need explicit `cacheFormat`; local vLLM discovery cannot infer server tool-call support, so tools start disabled. Native OpenRouter package use is recommended to preserve its request/reasoning behavior. These are examples of real compatibility work required beyond listing a model. [V2 models, prompt caching/local sections](https://opencode.ai/v2/docs/models); [V2 providers, gateways/runtimes](https://opencode.ai/v2/docs/providers)
- **Current vendor coupling also reaches product behavior.** Claude Code's live model configuration documents model-specific effort/contexts, minimum client versions for some models, model-driven defaults and automatic fallbacks, and provider-specific alias resolutions. This is evidence that adapting the harness for a new model can be substantive. Do not treat its vendor descriptions of which model is “most capable” as independently validated comparative results. [First-party Claude Code model configuration, retrieved Oct 15](https://code.claude.com/docs/en/model-config)
- **Avoid stale general claims about productivity.** In Feb 24, 2026, METR explicitly said its early-2025 finding of experienced developers being slowed by AI should not be assumed current: the later experiment suffered selection effects and concurrent-agent measurement problems. It believed speedups likely increased, but its new data were weak evidence of magnitude. This is neither proof of universal 2026 gains nor a valid basis to say agents still categorically slow developers. [Independent METR update, Feb 24, 2026](https://metr.org/blog/2026-02-24-uplift-update)

### Inferences
- **Best formulation:** commoditization of *access to useful capability* can advance while frontier models remain differentiated. A neutral harness can benefit from price/quality competition and task-specific model choice without relying on the stronger and unsupported proposition that “the models are all the same.” [Transfer and differentiated scores](https://arxiv.org/html/2603.28052v1); [provider-aware compatibility evidence](https://opencode.ai/v2/docs/models)
- **A stable neutral harness is a place to accumulate engineering improvements independently of supplier churn.** Research showing transferable retrieval improvements supports this as a plausible design bet, not proof all coding workflows transfer unchanged. Conversely, a provider's tightly co-designed harness may legitimately outperform generic implementations. [Meta-Harness](https://arxiv.org/html/2603.28052v1); [vendor harness reuse rationale](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli)
- **Do not conflate vendor-native API capability with vendor-product capability.** Passing a reasoning/cache/transport option through a provider adapter can preserve API features; it does not reproduce a vendor's cloud sessions, proprietary integrations, workspace identity, or internal orchestration. Codex's auth-dependent cloud/plugin features provide an actual example of that boundary. [V2 provider-specific runtime support](https://opencode.ai/v2/docs/providers); [Codex feature restrictions by auth](https://developers.openai.com/codex/auth)

### Gaps
- No defensible fresh October 15 cross-vendor ranking or comprehensive model-convergence statistic was established. March experiments and METR's discontinued dashboard must not be relabeled “current frontier results.”
- No direct experimental benchmark comparing OpenCode V2 to the exact current Codex/Claude Code/Antigravity releases was found or relied upon. Feature availability in docs is not measured reliability, equivalent safety, or equivalent performance.
- No proof that OpenCode captures every provider-specific capability on day one. Adapter support can lag; exact lag, release cadence, and behavioral parity were not measured.

## 3. What portability do MCP and skills buy, and is neutrality a durable advantage?

### Takeaway
MCP and skills make integrations and procedural knowledge more reusable, but they do not standardize the complete agent, its memory, permission policy, session state, or execution semantics. OpenCode V2's stronger philosophical claim is separating a user's enduring work/execution layer from the chosen intelligence supplier; its strongest challenge is that integrated vendors can adopt the same standards while bundling better economics and deeper model-specific execution. [MCP architecture](https://modelcontextprotocol.io/specification/2025-11-25/architecture); [Skills specification](https://agentskills.io/specification); [V2 state ownership](https://opencode.ai/v2/docs/troubleshooting)

### Cited Findings
- **The MCP specification explicitly leaves the host in charge.** The **Nov 25, 2025** version, fetched in full, makes the host responsible for client lifecycle, connection permissions, security/consent, user authorization, LLM sampling integration, and context aggregation. Full conversation history stays with the host; servers receive necessary context, not the whole conversation. Capability negotiation means implementations need not support every feature. This is the strongest precise citation for “a standard tool connector does not remove harness power.” [MCP architecture specification](https://modelcontextprotocol.io/specification/2025-11-25/architecture)
- **Skills standardize a package, not a runtime contract for everything it can do.** Current undated Agent Skills spec requires a directory with `SKILL.md` containing name/description plus Markdown instructions; optional scripts/references/assets and `compatibility` express environment requirements. `allowed-tools` is explicitly experimental and support varies between implementations; supported script languages depend on implementation. Progressive disclosure standardizes a useful loading pattern without guaranteeing identical invocation decisions or enforcement. [Agent Skills specification](https://agentskills.io/specification)
- **Concrete Google implementation difference:** Apr 30, 2026 Gemini CLI skill docs describe model-selected activation through `activate_skill`, then a user consent prompt; approval injects instructions and expands allowed file paths to the skill directory. It supports shared `~/.agents/skills` and workspace `.agents/skills` aliases. A portable folder therefore enters a particular host's consent and context model. This is Gemini CLI behavior, not a verified statement of all current Antigravity behavior. [First-party implementation docs](https://geminicli.com/docs/cli/skills)
- **Vendor harnesses already make standards useful.** Anthropic's **Sep 29, 2025** SDK article describes reusing the Claude Code harness for noncoding agents, with context gathering, subagents, compaction, tools, verification, and MCP integrations. Older evidence of the architecture, not a complete October 2026 SDK feature list. The article supports the counterargument that one can get custom workflows/integrations while retaining a vendor-native execution loop. [Anthropic SDK article](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)
- **OpenCode V2 is demonstrably more than a model dropdown.** Its troubleshooting page explicitly says a shared background server owns sessions, plugins, permissions and other state; it exposes service discovery/lifecycle and authenticated API inspection; the usual DB is `~/.local/share/opencode/opencode.db`. Its separate provider page makes native/custom/local model backends selectable. Together these establish the architectural separation of model supply from a persistent harness-owned execution/state layer. They do not establish universal state export between harnesses. [V2 service/state](https://opencode.ai/v2/docs/troubleshooting); [V2 backends](https://opencode.ai/v2/docs/providers)
- **Even intra-harness portability has boundaries.** V2 model docs say selection is per session, switching model does not rewrite configuration, and credentials/catalog/configuration are location-scoped; a model available in one project may not be available elsewhere. It documents shared machinery without claiming all authorization/config follows automatically. [V2 models](https://opencode.ai/v2/docs/models)

### Inferences
- **Useful analytical portability ladder:** (1) model endpoint/credentials, (2) tools/connectors, (3) instructions/skills/scripts, (4) active sessions/memory/artifacts, (5) permissions/sandbox guarantees, (6) organizational workflows/audit/governance. The sources concretely support interoperability at parts of 1–3 while leaving much of 4–6 with the host. This ladder is our synthesis, not an existing formal standard. [V2 provider adapters](https://opencode.ai/v2/docs/providers); [MCP host responsibilities](https://modelcontextprotocol.io/specification/2025-11-25/architecture); [Skills implementation caveats](https://agentskills.io/specification); [Codex identity/governance](https://developers.openai.com/codex/auth)
- **The philosophical significance is the locus of continuity.** If work state, trust decisions and custom procedures remain in a provider-neutral runtime, changing model suppliers need not mean changing one's entire workbench. That is a coherent anti-lock-in position even when models are not commodities. But it shifts trust to another harness maintainer; it does not abolish the need to trust or govern an execution platform. [V2 server-owned state](https://opencode.ai/v2/docs/troubleshooting); [V2 credential custody](https://opencode.ai/v2/docs/cli/providers); [MCP host security duties](https://modelcontextprotocol.io/specification/2025-11-25/architecture)
- **Neutrality ≠ automatic safety or user sovereignty.** Open source plus local state can improve inspectability/exit possibilities, but whether users actually have usable backups/export, secure credential storage, policy enforcement, and reliable execution remains an implementation/operations question. The docs establish a local DB and credentials there, not a security audit or formal portability guarantee. [V2 state/credential docs](https://opencode.ai/v2/docs/troubleshooting); [V2 credentials](https://opencode.ai/v2/docs/cli/providers)
- **Strongest counterargument to durable neutrality advantage:** integrated vendors can combine models trained/co-adapted for their tools, early access to new API behavior, bundled subscriptions/compute, managed cloud execution, and enterprise identity/compliance, while supporting the same MCP/skills ecosystem. If workflows/integrations themselves become portable standards, an independent harness cannot rely on standards support as a unique moat. It must continue winning on execution quality, reliability, local control, policy flexibility, provider switching or genuinely distinctive workflows; a dropdown alone is easily copied. This is a strategic inference, not proof vendors inevitably win. Concrete support: Google publicly chooses one shared server-side harness; Claude distributes its own harness via SDK and allows hosting its binary; Codex supports alternative providers while differentiating cloud/workspace features by authentication. [Google](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli); [Anthropic SDK](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk); [Anthropic binary-hosting policy](https://code.claude.com/docs/en/legal-and-compliance); [Codex auth/custom providers](https://developers.openai.com/codex/auth)
- **Best response to that counterargument:** neutrality is an option value and governance commitment, not necessarily an exclusive feature moat. Users may accept some integration lag to avoid tying accumulated work/trust arrangements to a supplier's pricing, model roadmap and identity service. Native adapters plus local models make the exit credible, but whether this outweighs integrated-product convenience is user/task-dependent, not established empirically here. [V2 backends/adapter mechanisms](https://opencode.ai/v2/docs/providers); [provider-specific behavior](https://opencode.ai/v2/docs/models); [upstream policy leverage](https://code.claude.com/docs/en/legal-and-compliance)
- **Suggested report sentence:** “The radical part is not that OpenCode can call several models. It is the proposal that the environment which remembers your work, grants permission and runs tools should not belong to the company supplying the intelligence.” Label as the writer's interpretation of the documented architecture, not an official OpenCode quotation. [V2 state layer](https://opencode.ai/v2/docs/troubleshooting); [V2 provider choice](https://opencode.ai/v2/docs/providers)

### Gaps
- MCP reference here is an explicitly versioned November 2025 architecture, not verified to be the newest specification as of October 2026. Its scoped host-responsibility statements are still the cited evidence; do not claim all subsequent extensions were reviewed.
- No general cross-harness standard for migrating live conversation state, permission rules, OAuth sessions, memory or full agent workflows was established. Absence from these sources is not proof none exists.
- Durability of neutrality as a commercial moat is fundamentally uncertain. The evidence identifies competing forces; it does not forecast market share or prove OpenCode's current reliability.
